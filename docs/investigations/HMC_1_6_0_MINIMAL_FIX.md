# HMC 接口兼容与首次通知 Flow 收集

## 基线与范围

直接从官方 HyperModifier `v1.6.0` / `c733d97fc29b0e6f46a3675dce571381c0f7aa4e`
创建本地分支 `fix/hmc-v1.6.0-minimal`。没有以之前的修复提交为父提交，也没有合并它的整套变更。
复核后保留必要的接口适配代码和对应测试；本轮尚未上传 fork，也不创建 PR。

## 两个不同的故障

### 1. 官方版本的 HMC 新版接口解析失败

官方 v1.6.0 的解析器与 v1.5.3 相同，假定指纹避让/隐藏设置是静态基本类型字段。
HMC v0.9.50、v0.9.55 已改为设置对象内的 volatile 实例值，正式 APK 中 getter 被 R8 内联为实例字段读取。
因此旧解析器找不到 `fpAvoid`，报 `HMC fingerprint avoidance: expected one match, found 0`。

解析还必须识别 `postInvalidate()`，以及新版 ClockRoom 中同签名的展开分支和独立重置方法；
否则通过第一个字段后还会在后续成员解析中失败。所有调整均在接口识别/读取层，未改动 HMC 设置。

### 2. 解析通过后，1.6.0 错过首次通知 Flow 收集

用户对 1.5.3 测试包确认展开、收起正常；对 1.6.0 首个测试包反馈：

```text
HMC 展开通知下沉
未捕获首次通知 Flow 收集，请启用扩展后重启系统界面
```

之前只比较 HMC 类，遗漏了 `MyHyperModifier` 入口调度的变化：
v1.5.3 在 `startEarlySystemUiHooks()` 中安装扩展，v1.6.0 则移到首帧后 300 ms 的后台任务，
无首帧时使用 10 秒后备任务。通知 combine 是启动时即开始收集的 Flow；
Hook 如果此后才安装，就捕获不到原来的输入数组和供展开/收起触发通知更新的策略 Flow。
HMC v0.9.55 的 `NotificationSink` 源码也明确说明了这种一次收集的约束。

报错本身仅证明策略 Flow 未捕获；结合入口差异，安装时序是本轮修复针对的原因。
这不能用单纯更改 DEX 成员解析解决。最终是否覆盖用户设备的全部原因仍需实机复测。

问题均位于 HyperModifier 对 HMC 的兼容/接入侧；现有证据不要求修改 HyperMusicCover 模块。

## 最小生产代码调整

| 文件 | 调整 |
| --- | --- |
| HyperMusicCoverDexSymbols | 识别设置对象、实例值、指纹重绘及新版时钟内部成员，保留旧版解析 |
| HyperMusicCoverSymbols | 从解析结果构造只读设置访问器 |
| HyperMusicCoverSetting（新增） | 缓存 Field 元数据，读取实时设置值，不写入 HMC |
| HyperMusicCoverAdapter | 接收新版设置访问器 |
| HyperMusicCoverExtensions | 两处设置读取适配；将现有通知监听安装拆为一次性入口，跨线程可见 |
| MyHyperModifier | 仅新增三行，在早期阶段调用通知监听安装 |

`HyperMusicCoverNotificationFlow` 和 `HyperMusicCoverExtensionPolicy` 与官方 1.6.0 完全一致。
通知偏移计算、展开判断、指纹绘制与恢复、HMC 绑定、时钟行为不作逻辑调整。
其余 Hook 仍按官方 1.6.0 延迟安装；保留模块开关、兼容模式和崩溃保护入口。
延迟阶段再次调用通知安装时，由独立原子标记防止重复注册。

## 性能范围

接口 DEX 解析仍沿用原后台解析路径；高频路径只读取已缓存 Field 元数据。
通知 Hook 的数量、回调内容和 Flow 数量不变，启动阶段将原有一次 OEM DEX 类名扫描及少量类解析/Hook 安装提前。
这是此次时序修复的启动成本，不等于零开销；未将整个扩展或其他 SystemUI Hook 提前。
未新增轮询、定时常驻任务、主线程 IPC 或渲染层。没有真机启动耗时、帧率或耗电对照数据。
